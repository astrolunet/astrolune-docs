# 3. Виртуальная машина (ALVM) и модель ресурсов

## 3.1. ALVM v1 — исполнение

**Статус: реализовано, consensus-visible.**

ALVM — детерминированная 64-битная стековая машина. Значения — беззнаковые
u64. Арифметическое переполнение, деление на ноль, некорректный доступ к
памяти, неправильная форма стека, неизвестные опкоды и неизвестные
host-вызовы приводят к trap (ловушке). Нет плавающей точки, часов,
многопоточности, файловой системы, сети, JIT или окружающего состояния
процесса.

### Контейнер

Развёрнутая программа — один канонический контейнер:

| Поле | Кодировка |
|---|---|
| magic | четыре байта `ALVM` |
| версия контейнера | u16-le, ровно 1 |
| версия ISA | u16-le, ровно 1 |
| флаги | u32-le, ноль в v1 |
| количество функций | минимальный varint, 1..1024 |
| функции | дескрипторы по количеству |
| длина кода | минимальный varint, 1..1 МиБ |
| код | байты инструкций, без хвостовых данных |

Дескриптор: `offset:u32, parameters:u16, results:u16, max_stack:u16,
reserved:u16`. Reserved — ноль. Функция ноль — точка входа по умолчанию,
без параметров. Транзакция может выбрать любой дескриптор с нулём
параметров как точку входа. ABI-имена и метаданные исходного языка — вне
консенсусного контейнера.

### Валидация деплоя

`al_vm_validate` и `al_vm_program_load` используют scratch-память арены,
предоставленной вызывающим, и не аллоцируют через malloc/free. Валидация
предекодирует весь раздел кода, затем проверяет каждую функцию независимо:

- каждый опкод и номер хоста известны;
- непосредственные значения и границы функций полны и упорядочены;
- цели переходов остаются внутри текущей функции и попадают на инструкцию;
- каждое достижимое слияние имеет одну идентичную высоту стека;
- каждый путь остаётся в пределах лимитов стека дескриптора и genesis;
- сигнатуры внутренних вызовов совпадают с заявленными эффектами pop/push;
- функция ноль завершается STOP, RETURN или REVERT;
- функции, достигаемые через CALL, следуют протоколу фрейма и завершаются RET;
- функция, не являющаяся нулевой и на которую не указывает ни один CALL,
  может быть чистой точкой входа: ноль параметров, завершается RETURN или
  REVERT, чтобы уровень транзакции получил данные возврата. Смешивание
  обоих протоколов в одной функции отклоняется — RETURN разрушило бы
  фреймы вызывающего;
- финальная инструкция каждой функции — терминатор.

Недостижимые байты всё равно декодируются и должны быть валидны — это
не даёт спрятать вторую интерпретацию за control flow.

### Исполнение

Исполнение использует арену, предоставленную вызывающим, для стека,
линейной памяти, фреймов вызовов, отслеживания активных адресов и данных
возврата. Линейная память имеет genesis-лимит и инициализирована нулями.
LOAD64 и STORE64 явно little-endian.

Внутренние вызовы синхронны и ограничены 64 фреймами по умолчанию. Вызовы
контрактов также синхронны. Дочерний REVERT восстанавливает свой
стейджинговый корень состояния и события, затем возвращает
статус/данные вызывающему. Любой другой дочерний trap завершает всю
транзакцию. Стек активных адресов отклоняет вызов любого текущего
активного контракта с `AL_ERR_REENTRANCY`.

### Host ABI

HOST несёт u16-номер хоста. Аргументы снимаются со стека VM, результаты
кладутся в порядке объявления.

| ID | Операция | Форма стека |
|---:|---|---|
| 0 | записать адрес отправителя в память | (offset) -> () |
| 1 | записать текущий адрес | (offset) -> () |
| 2 | высота блока | () -> (height) |
| 3 | протокольный день | () -> (day) |
| 4 | баланс аккаунта | (address_offset) -> (balance) |
| 5 | перевод от текущего контракта | (address_offset, amount) -> () |
| 6 | получение из хранилища | (key_off,key_len,out_off,out_cap) -> (len) |
| 7 | запись в хранилище | (key_off,key_len,val_off,val_len) -> () |
| 8 | удаление из хранилища | (key_off,key_len) -> () |
| 9 | выпуск события | (topic_off,topic_len,data_off,data_len) -> () |
| 10 | тегированный хеш | (data_off,data_len,out_off,tag_id) -> () |
| 11 | проверка подписи | (hash_off,pubkey_off,signature_off) -> (valid) |
| 12 | вызов контракта | (addr_off,value,in_off,in_len,out_off,out_cap) -> (status,len) |

Хост тегированного хеша принимает только стабильные ID `al_vm_hash_domain`:
данные контракта, адрес, ключ/значение хранилища, событие, запись PoTB,
транзакция и блок. Неизвестные ID приводят к trap `AL_ERR_OUT_OF_RANGE`;
байткод не может подставить произвольную строку домена.

Системный аккаунт PoTB недостижим через хосты хранилища. Только нативные
переходы консенсуса используют мост состояния системы.

### Ресурсы

Стоимость вычисления опкодов и хостов берётся из
`al_vm_resource_schedule` в genesis. Память — пиковое число тронутых страниц
по 4 КиБ. Storage I/O сообщается стейджинговой транзакцией состояния.
Пропускная способность взимается уровнем транзакции. Каждое сложение и
сравнение с лимитом использует проверяемую целочисленную арифметику.

### Арифметика и control flow

ADD, SUB и MUL trap при беззнаковом переполнении. DIV и MOD trap при нуле.
Счётчики сдвига от 64 и выше дают ноль. Доступы к памяти проверяются на
границы до любого чтения/записи. Прыжки — статические смещения внутри
текущей функции; динамических и межфункциональных прыжков не существует.

### Извлечение байта и знаковое расширение

BYTE извлекает байт на позиции `p` (0 = самый значимый) из 64-битного
значения. Для позиций вне 0..7 результат — ноль.

SIGNEXTEND трактует первый аргумент как число байт (0..7) для знакового
расширения. Для `b < 8` знаковый бит находится на позиции `b*8 + 7`. Все
старшие биты устанавливаются, если знаковый бит установлен, иначе
очищаются. Для `b >= 8` значение проходит без изменений.

### Память и хранилище

MLOAD и MSTORE — 8-байтные (u64) загрузки и записи, little-endian,
используют ту же линейную память, что и LOAD8/STORE8. SLOAD и SSTORE
обращаются к парному хранилищу ключ-значение конкретного контракта через
транзакцию состояния. Ключи и значения — байтовые слайсы произвольной
длины, на которые ссылаются пары (offset, length) в памяти.

### Контекст исполнения

ADDRESS пишет 32-байтный текущий адрес контракта в память по заданному
смещению. CALLER пишет 32-байтный адрес отправителя транзакции. CALLVALUE
кладёт значение вызова транзакции как u64 на стек. CODESIZE кладёт длину
исполняемого кода. CODECOPY копирует диапазон исполняемого кода в память.

### RETURN и REVERT

RETURN и REVERT разворачивают всю машину, так что легальны только там, где
над ними ничего не нужно возобновлять: в функции ноль, и в ненулевых
функциях, на которые ничего не указывает CALL — они служат точками входа
транзакции, возвращающими данные (ноль параметров). Всё, достижимое через
CALL, завершается RET. Валидатор статически принуждает это разделение.

### Расписание стоимостей

Таблица выше — расписание разработки по умолчанию. Genesis несёт стоимость
каждого опкода и хоста, валидация отклоняет нулевые и `UINT64_MAX`
стоимости. Изменение расписания — это изменение идентичности цепи, а не
локальная настройка.

## 3.3. Модель ресурсов и комиссий v1

**Статус: реализовано; продакшен-цифры требуют бенчмарк-калибровки.**

Astrolune измеряет четыре независимых беззнаковых 64-битных измерения:

| Измерение | Определение |
|---|---|
| compute | сумма стоимостей опкодов и хостов genesis вдоль исполненного трейса |
| memory | пиковое число тронутых страниц по 4 КиБ, включая синхронные дочерние вызовы |
| storage | канонический ключ плюс байты старого/нового значения, прочитанные или записанные |
| bandwidth | точный размер канонической подписанной транзакции |

Каждая транзакция несёт вектор лимитов и вектор максимальной базовой цены.
Каждый блок несёт фактическое совокупное использование и вектор цен,
использованный для этого блока. Арифметическое переполнение — ошибка
исполнения/консенсуса; счётчики никогда не насыщаются.

### Базовая цена

Каждая цена ресурса эволюционирует независимо от использования родителя.
Genesis-цель обычно — 50% от лимита блока. Для цены P, использования U и
цели T:

```
delta = floor(P * abs(U - T) / T / 8)
```

Выше цели, следующая цена — `P + max(delta, 1)`. Ниже цели — `max(P -
delta, 1)`. На цели — без изменений. Таким образом, полный блок против
50%-й цели двигает цену максимум на 12.5%, а минимальная цена — единица.

Фактическая базовая комиссия — проверяемое скалярное произведение
фактического использования и текущих цен. Она списывается с отправителя и
сжигается. Чаевые транзакции выплачиваются полностью после включения
исполнения и делятся на бакеты PoTB 60/25/15; остаток от целочисленного
округления идёт в плоский бакет.

### Семантика отказов

Кодирование, размер/тип, цепь/истечение срока, nonce, ресурсно-балансовые
границы и подпись проверяются в этом порядке. Отказ pre-validation ничего
не меняет.

После начала исполнения:
- успех коммитит записи/значение, увеличивает nonce, сжигает фактическую
  базовую комиссию и платит полные чаевые;
- REVERT или trap восстанавливает все записи исполнения и перевод
  значения, но всё равно увеличивает nonce, сжигает фактически
  использованную базовую комиссию и платит полные чаевые;
- неиспользованный ресурсный лимит никогда не взимается;
- депозиты хранения — залог состояния, не комиссия.

### Депозит хранения

Рост хранилища контракта блокирует `deposit_per_byte` с баланса этого
контракта. Уменьшение или удаление значения возвращает точный
соответствующий депозит тому же контракту. Зарезервированное системное
пространство имён PoTB поддерживается нативными переходами консенсуса и
освобождено от обычных депозитов контрактов.

Продакшен-лимиты блока и цены намеренно не захардкожены в этой
спецификации. Это значения genesis, которые должны быть выбраны из
бенчмарк-данных для минимального поддерживаемого железа валидатора — см.
раздел 7 про требования к валидатору.
