# 5. Языки смарт-контрактов: Trocto (.tc) и Regol (.rg)

**Статус: v0.2 реализована.** `tools/` содержит компилятор (C++23, таргет
`trocto`) с обоими уровнями, связанными сквозь весь конвейер: Trocto
опускается до Regol, Regol ассемблируется в контейнер ALVM, каждый
артефакт повторно валидируется через тот же `al_vm_validate`, что и деплой.
`tests/cxx/test_lang.cpp` исполняет скомпилированные контракты на реальной
VM против мок-хоста; `examples/counter.tc` и `examples/token.tc` —
референсные примеры.

## 5.1. Принцип: два уровня одной системы, а не два независимых языка

Модель та же, что использует Ethereum с Solidity/Yul, или Aptos/Sui с
Move/Move-IR: высокоуровневый язык компилируется в низкоуровневый, а не
существует рядом с ним.

```
Разработчик пишет .tc  →  Компилятор Trocto  →  Regol (.rg)  →  Байткод VM
                                                     ↑
                        продвинутый разработчик может писать .rg напрямую
```

## 5.2. Trocto (.tc) — высокий уровень, безопасность по умолчанию

**Для кого:** основная масса разработчиков — токены, NFT, игровая логика,
стандартные протоколы.

**Принципы:**
- Безопасность по умолчанию — защита от типичных уязвимостей контрактов
  встроена в компилятор (переполнение целых чисел, реентерабельность,
  непроверенные вызовы), по аналогии с тем, как Solidity 0.8+ сделал
  проверки переполнения стандартом, а не опцией.
- Читаемый, декларативный синтаксис — цель в том, чтобы разработчик с
  опытом Solidity/TypeScript мог начать писать на Trocto без долгого
  разгона.
- Намеренно ограниченный доступ к низкоуровневым примитивам, чтобы по
  умолчанию нельзя было случайно выстрелить себе в ногу.

**Не для:** ситуаций, требующих точного контроля над потреблением ресурсов
(gas/исполнение) или доступа к возможностям VM, которые Trocto намеренно
скрывает ради безопасности.

## 5.3. Regol (.rg) — низкий уровень, полный контроль

**Для кого:** продвинутые разработчики, инфраструктурные протоколы и
авторы библиотек, чьи библиотеки затем становятся основой для контрактов
на Trocto.

**Принципы:**
- Прямой доступ к примитивам VM без защитных обёрток Trocto.
- Точный контроль над потреблением ресурсов — важно для высоконагруженных
  протоколов (DEX, ончейн-игры с частыми вызовами), где важна каждая
  единица газа.
- Меньше защиты «из коробки» — ответственность за безопасность лежит на
  разработчике, как и в любом языке, близком к уровню байткода.

**Также:** это язык, в который компилируется Trocto — так что Regol не
только напрямую доступен, но и является промежуточным представлением
(IR) всей системы компиляции.

## 5.4. Синтаксис Trocto — пример

Черновой пример — простой контракт взаимозаменяемого токена, для
фиксации ощущения синтаксиса:

```rust
contract Token {
    state {
        name: string,
        total_supply: u64,
        balances: map<address, u64>,
    }

    // конструктор — вызывается один раз, при деплое
    init(name: string, initial_supply: u64) {
        self.name = name;
        self.total_supply = initial_supply;
        self.balances.insert(sender(), initial_supply);
    }

    // строгая типизация плюс обязательные проверки предусловий (require)
    pub fn transfer(&mut self, to: address, amount: u64) -> Result<(), Error> {
        require(self.balances[sender()] >= amount, Error::InsufficientBalance);
        require(to != address::zero(), Error::InvalidAddress);

        self.balances[sender()] -= amount;   // переполнение проверяется по умолчанию
        self.balances[to] += amount;

        emit Transfer { from: sender(), to, amount };
        Ok(())
    }

    pub fn balance_of(&self, owner: address) -> u64 {
        self.balances.get(owner).unwrap_or(0)
    }
}
```

**Что уже показывает пример, и что стоит закрепить как принципы синтаксиса:**
- `contract` вместо связки `struct` + `impl` из Rust — выделенная
  конструкция для смарт-контрактов;
- `state { }` — явный, отделённый блок хранимых в блокчейне данных (сразу
  видно, что «живёт» между вызовами, а что временно);
- `Result<(), Error>` и `require(...)` — заимствование у Rust идеи явной
  обработки ошибок вместо тихих исключений;
- целочисленные операции (`+=`, `-=`) проверяются по умолчанию (никаких
  `wrapping_*`/`unchecked` без явного запроса — в отличие от чистого Rust,
  где переполнение молча оборачивается в release-сборке);
- `emit` для событий — знакомая концепция из Solidity, без нарушения
  похожести на Rust;
- `pub fn` / `&mut self` / `&self` — прямое заимствование синтаксиса
  методов и мутабельности Rust, чтобы разработчики с опытом Rust могли
  читать Trocto почти без изучения.

## 5.5. Реализованное подмножество: Trocto v0.2

Уровень v0.2 добавляет конструкторы, строковые литералы, расширенные типы
карт и систему импорта поверх целочисленного фундамента v0.1.

```rust
contract Token {
    state {
        total_supply: u64,
        balances: map<address,u64>,
        allowances: map<address,u64>,
    }

    init(initial_supply: u64) {              // конструктор
        self.total_supply = initial_supply;
        balances[sender()] = initial_supply;
        emit Transfer(0, initial_supply);
    }

    pub fn transfer(to: address, amount: u64) -> u64 {
        let b = balances[sender()];
        require(b >= amount, 2);              // переполнение — trap от VM
        balances[sender()] = b - amount;
        balances[to] += amount;
        emit Transfer(amount, 1);
        return 1;
    }

    pub fn balance_of(owner: address) -> u64 {
        return balances[owner];
    }
}
```

Поверхность грамматики (дополнения v0.2 к v0.1):
- `init(...)` — конструктор, компилируется как точка входа по умолчанию
  (функция 0). Вызывается один раз при деплое; получает calldata как
  публичная функция.
- `import "path";` — импорт на уровне файла или контракта. Импортируемый
  файл парсится и валидируется; линковка функций запланирована на v0.3.
- `"string"` — строковые литералы, материализуются в линейной памяти.
- `assert(cond);` — паника с revert-кодом 0 (неисправимое утверждение).
- `map<u64,u64>`, `map<address,u64>`, `map<address,address>` — расширенные
  комбинации типов ключ/значение карты.
- Тип `address` для параметров, локальных переменных и ключей карт.

Фиксированные решения, за которые отвечает компилятор:

- **Ключи состояния.** Ключ хранилища поля —
  `tagged_hash(домен contract_data, "field.<contract>.<name>")`,
  вычисляется на этапе компиляции и встраивается как константы.
  Отсутствующие слоты читаются как ноль.
- **Публичный ABI.** Каждая `pub fn` компилируется в функцию ALVM без
  параметров: пролог валидирует длину calldata (revert-код 1 при
  несовпадении) и декодирует n×8 little-endian аргументов во фреймовые
  слоты; результаты возвращаются через RETURN из зарезервированной памяти.
- **Протокол фрейма.** Обычные `fn` используют VM CALL/RET со стековыми
  параметрами; публичные функции в v0.1 внешние-only (вызвать одну изнутри
  другой — ошибка компиляции, поскольку RETURN разрушит фреймы
  вызывающего).
- **События.** `emit Name(…)` хеширует имя в домене событий для своего
  топика и сериализует аргументы u64 в линейную память.
- **Расположение памяти** на функцию: `[0,32)` — scratch ключ/топик,
  `[32,64)` — scratch данные/код возврата, `[64,72)` — слот результата,
  затем локальные переменные и декодированные параметры. Все смещения
  статичны; нет динамического выделения памяти.

Пока не реализовано (отслеживается в открытых вопросах): импорты
валидируются, но линковка функций ещё не реализована (v0.3); дженерики,
типы ресурсов и стандартная библиотека.

## 5.6. Regol v0.1

Текст Regol — видимое IR: мнемоники отображаются 1:1 на таблицу ISA, с
именованными функциями, определениями `.label`, символьными целями
переходов и именованными хостами (`host storage_get`). Первая функция —
точка входа по умолчанию, без параметров, отражая контракт-контейнер.
`trocto --emit-regol` печатает опущенную форму любого контракта Trocto;
этот вывод ассемблируется обратно в эквивалентный контейнер.

## 5.7. Kreep — отклонён

Третий язык (Kreep, `.kp`) для внутреннего сетевого инструментария
рассматривался изначально. Решение — против: он не нужен как отдельный
язык. Сетевой инструментарий (CLI, RPC, индексатор) разрабатывается на C++.

## 5.8. Открытые вопросы для дальнейшей работы

1. ~~Точный синтаксис Trocto~~ — зафиксирован: похожий на Rust. Осталось
   доделать: полный список ключевых слов, систему модулей/импорта,
   дженерики.
2. Система типов — ресурсная модель (как в Move, для строгого контроля
   токенов/NFT как объектов, которые нельзя случайно передать) или
   классическая.
3. Модель ценообразования gas/исполнения — как стоимость операции
   вычисляется в Trocto и в Regol.
4. Стандартная библиотека — какие стандарты встроить с самого начала
   (эквиваленты ERC-20/ERC-721) для токенов и NFT.
5. Формальная верификация — нужен ли инструмент вроде Move Prover для
   критичных контрактов на Regol.

Пункты 2 и 3 блокируют компилятор: ни проверщик типов, ни генератор кода
не могут быть написаны без них. Это причина, по которой спецификация языка
находится в конце дорожной карты, а не в начале.
