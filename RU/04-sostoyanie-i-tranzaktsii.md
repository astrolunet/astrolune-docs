# 4. Состояние, транзакции и блоки

## 4.1. Модель состояния v1

**Статус: реализовано с in-memory и долговременным бэкендами узла.
Дисковый бэкенд сохраняет этот интерфейс и остаётся вне консенсуса.**

### Аккаунты

Верхнее дерево состояния отображает тегированные 256-битные хеши адресов
на фиксированные значения аккаунтов:

| Поле | Значение |
|---|---|
| address | полный 32-байтный адрес аккаунта |
| balance | доступный к трате объём токенов |
| nonce | следующий последовательный nonce транзакции |
| code_hash | ноль для пользователей; SHA-256 неизменяемого контейнера ALVM для контрактов |
| storage_root | корень независимого SMT-хранилища этого контракта |
| storage_bytes | текущий объём хранимых байт значений |
| storage_deposit | залог, заблокированный под эти байты |

Код контракта неизменяем и адресован по содержимому. Апгрейд означает
деплой по новому адресу и явную миграцию состояния; ни опкод, ни API
состояния не заменяют код.

### Двухуровневое разреженное дерево Merkle

Оба уровня — сжатые depth-256 бинарные разреженные деревья Merkle. Ключи
аккаунтов используют `AL_TAG_ACCOUNT_KEY(address)`. Ключи хранилища
контракта используют `AL_TAG_STORAGE_KEY(key)`. Листья и ветви используют
разные доменные теги SMT, значения аккаунта и хранилища — разные теги
значений. Пустые хеши детерминированы на каждой глубине.

Доказательство SMT содержит полный ключ, бит существования, хеш значения,
256-битную битовую карту соседей и только не-дефолтные соседи в порядке
от корня к листу. Декодер отклоняет неканонические счётчики, невозможные
значения отсутствия, некорректные битовые карты, усечение и хвостовые
байты. Один формат доказывает и членство, и отсутствие.

### Контракт хранилища

Consensus-слой получает `al_state_store` с контекстом, предоставленным
вызывающим, и четырьмя колбэками: неизменяемое получение/запись узла и
неизменяемое получение/запись значения. Запись под существующим хешем
должна содержать идентичное содержимое. Ядро не владеет базой данных и не
удерживает буферы вызывающего.

`al_state_memory_store` — детерминированный линейный бэкенд для тестов,
фаззинга и малых симуляций. Бэкенд узла append-only индексирует те же
неизменяемые объекты на диске и коммитит канонические байты блока только
после синхронизации файлов состояния. Недостижимые content-addressed узлы
могут физически оставаться в любом из бэкендов; только узлы, достижимые из
закоммиченного корня, являются логическим состоянием.

### Стейджинг и снапшоты

`al_state_txn_begin` копирует закоммиченный корень. Чтения и записи
работают против этого стейджингового корня. Коммит публикует его
атомарно; откат отбрасывает его. Снапшоты — пары (height, root) и
восстанавливают состояние реорга за константное время.

Проваленный вызов контракта восстанавливает свой подкорень. Проваленная
транзакция восстанавливает свой корень исполнения перед коммитом только
nonce и комиссий. Проваленный блок восстанавливает снапшот на входе в
блок.

### Хранилище и системное состояние

Обычные ключи хранилища — 1..256 байт, значения — не более 64 КиБ. Чистый
рост блокирует `deposit_per_byte` genesis у контракта; уменьшение
возвращает депозит. Байты storage I/O добавляются к стейджинговому вектору
ресурсов транзакции.

Записи PoTB живут в дереве хранилища детерминированного зарезервированного
системного адреса. Обычные методы хранилища и хосты байткода отклоняют
этот адрес. Только явно названный нативный мост системного хранилища
может изменять его.

## 4.2. Транзакции, квитанции и блоки v1

**Статус: реализовано.** Все целочисленные поля little-endian; все длины —
минимальные беззнаковые varint; хвостовые байты недопустимы.

### Подписанный конверт

| Поле | Кодировка |
|---|---|
| version | u16, ровно 1 |
| chain_id | u32 |
| expiry_height | u64 |
| sender | 32-байтный публичный ключ |
| nonce | u64, точный следующий nonce аккаунта |
| resource_limit | четыре значения u64 |
| max_base_price | четыре значения u64 |
| tip | u64 |
| type | u8 |
| body | зависит от типа |
| signature | 64 байта |

Четыре значения ресурса — compute, memory, storage и bandwidth.
Максимальный канонический размер транзакции — 1 МиБ. Батчинга в v1 нет.

| Тип | Значение | Тело |
|---|---:|---|
| transfer | 0 | recipient:address, amount:u64 |
| deploy | 1 | value:u64, container:varbytes |
| call | 2 | contract:address, value:u64, entrypoint:u32, calldata:varbytes |
| PoTB native | 3 | operation:u8, target:pubkey, amount:u64, data:varbytes |

Операции PoTB 0..9 — регистрация, аттестация, челлендж, ответ на
челлендж, доказательство нарушения, депозит залога, вывод залога, commit
сида, reveal сида и голос комитета. Этот слой коммитит их каноническое
доказательство в зарезервированное системное пространство имён.
Сохранённое значение содержит полное каноническое нативное тело:
операцию, цель, объём и доказательство. Группировка по корреляции,
согласование ASN и исследование эпохи намеренно не выдуманы реализацией
транзакций.

### Хеши и подписи

Подписываемый дайджест тегирован `AL_TAG_TX_SIGNING` и покрывает каждое
поле вплоть до тела, исключая подпись. Идентификатор транзакции тегирован
`AL_TAG_TX` и покрывает те же канонические поля плюс подпись. Эти домены
намеренно разные.

### Валидация и взимание

Порядок валидации фиксирован:
1. версия, кодирование, размер и форма типа/тела;
2. ID цепи и высота истечения срока;
3. точный nonce;
4. bandwidth, потолки цен ресурсов и худший случай списания баланса;
5. подпись.

Отказы на этом этапе ничего не взимают. После начала исполнения
`al_tx_apply` возвращает `AL_OK` для включённой транзакции и записывает в
квитанции успех исполнения, REVERT или trap. Включённые отказы потребляют
nonce, фактическую базовую комиссию и полные чаевые, восстанавливая
записи.

### События и квитанции

Событие содержит выпускающий контракт, тегированный хеш топика и
заимствованные данные. Кодировщики событий и квитанций имеют совпадающие
строгие декодеры; переменные данные остаются заимствованным представлением
канонического входа, а массивы событий квитанции используют арену
вызывающего. Квитанция коммитит:
- хеш транзакции и статус исполнения;
- фактическое четырёхмерное использование ресурсов;
- сожжённую базовую комиссию и уплаченные чаевые;
- адрес развёрнутого контракта, когда применимо;
- данные возврата;
- упорядоченные события, чьи хеши свёрнуты в хеш квитанции.

Кодировки квитанций и событий имеют независимые доменные теги. Блок
коммитит упорядоченный корень Merkle квитанций.

### Genesis

Канонический формат genesis фиксирует версию, ID цепи, начальный корень
состояния, лимиты блока, 50%-е цели, начальные базовые цены, ставку
депозита хранения, все стоимости опкодов/хостов, лимиты VM и полный набор
параметров PoTB. Валидация genesis отклоняет нулевые цены/лимиты/стоимости
и несогласованные параметры PoTB.

### Блоки

Фиксированный 338-байтный заголовок кодирует версию, ID цепи, высоту,
протокольный день, корни родителя/состояния/транзакций/квитанций,
фактическое использование ресурсов, текущие базовые цены, ключ проповера и
три адреса бакетов чаевых PoTB. Каноническое тело — заголовок, счётчик
транзакций, затем закодированные с длиной канонические транзакции.

Исполнение блока верифицирует связь с родителем, переход цены и корень
транзакций до исполнения. Оно применяет транзакции в порядке тела,
принуждая genesis-лимит блока, затем верифицирует корень состояния, корень
квитанций и точное совокупное использование. Любое несовпадение
восстанавливает снапшот на входе. Политика упорядочивания транзакций —
забота проповера/мемпула; валидация исполняет закоммиченный порядок.
